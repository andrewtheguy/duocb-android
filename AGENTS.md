- purpose: Android peer of the desktop duocb clipboard-sharing app, the sibling of `../duocb-ios`. Each installation holds its own application keypair (nsec) and a signed, expiring identity card naming `<short-name>_<permanent-suffix>`; trust is a local list of imported peer cards, not a shared secret. Two devices bootstrap trust with **card setup** (FFI roles `card_host`/`card_join`): a rotating PIN authenticates a short-lived connection (a SPAKE2 PAKE in the core), the cards cross it, and the user confirms one pairing code — built from both keys, rendered identically on the two screens (`DuocbNative.pairingCode`) — before either is stored; card setup never carries clipboard content. After that the two share the clipboard with one FFI role, `connect`: **both** devices pick the other from their trusted list, and the core decides which of them listens and which dials from the two application keys (`DuocbNative.sessionRole`) — the user is never asked, and the order the two press Connect in does not matter
- strict no backward compatibility, legacy codes, or changelogs at all
- make changes on the sibling project ../duocb (the Rust core + FFI this app loads) if needed; its Android surface is `crates/duocb-ffi/src/android.rs`, built by `./build-android.sh` there. Use ../duocb/CLAUDE.md for starting e2e tests on the desktop side for the opposite party
- **there is no "hub" FFI role.** The hub is pure local state — the trusted-device list is read from this app's own storage, nothing is broadcast and nothing is discovered — so no FFI handle exists while it is on screen. At most one handle runs at a time, and only for a session: `connect`, `card_host` or `card_join` (`SessionController`, owned by `DuocbApplication` so it outlives activity recreation)
- the signaling channel (`lan_then_nostr` default / `lan_only` / `nostr_only`) is the desktop's launch-fixed `--lan-only`/`--nostr-only`. Android has no CLI, so it is a Settings picker read when a session starts; it governs card setup and clipboard sessions alike, and **both devices must be set to a channel they share**; the PIN does not encode a channel
- the Rust artifact (`libduocb.so` per ABI, zipped as `libduocb-android.zip`) is delivered by download + sha256 pin in `gradle.properties` (`app/build.gradle.kts` `fetchDuocbJniLibs`). Bump with `scripts/bump-jnilibs.sh <tag>` after the duocb release workflow publishes the asset. For FFI dev against a local build run `../duocb/build-android.sh` then set `DUOCB_LOCAL_JNILIBS=1` for every gradle invocation — only the exact value `1` opts in. Until a release carries the Android asset, the pin's sha256 is empty and only the local build works
- `DuocbNative` must stay at `com.andrewtheguy.duocb.DuocbNative`: the JNI symbol names in ../duocb/crates/duocb-ffi/src/android.rs encode that class. `DuocbNative.init(context)` must run once before anything else (`DuocbApplication.onCreate`): it registers the JVM/context that iroh's Android DNS/interface discovery needs, or the first session aborts the process
- **targetSdk is pinned to 35 (Android 15) on purpose**, compileSdk 37 (Compose needs it). From targetSdk 37 Android gates every local-network socket — the in-process mDNS the core relies on — behind the `ACCESS_LOCAL_NETWORK` runtime permission; below that the `INTERNET` permission grants it implicitly on every Android version, and Google's guidance is not to declare or request the permission until the target is raised. Raising the target means adding that permission flow first
- **Android keeps the whole desktop core**: unlike iOS, nothing is compiled out — both the DNS-SD responder (mdns-sd) and iroh's own mDNS address lookup run in-process. What Android gates is *receiving* multicast on Wi-Fi, so `SessionController` holds a `WifiManager.MulticastLock` for the life of every session on a LAN channel (`CHANGE_WIFI_MULTICAST_STATE`). Without it the LAN rendezvous silently never resolves and reads like a network problem
- persistence splits by sensitivity, not by convenience: the application private key, permanent 8-char suffix, and iroh transport key live AES-GCM-encrypted under an AndroidKeyStore key in a private SharedPreferences file (`SecretStore.kt` → `DuocbSecrets`); the device name, this device's signed self-card, trusted peers' cards, and channel live in a JSON file under `files/duocb/config.json` (`ConfigStore.kt`, atomic temp-and-rename). The non-secret fields shared with the desktop use the same snake_case names (`DuocbConfig`). `allowBackup` is off: an identity *is* this installation. Commit points: the key the moment it is generated/imported, the name and its freshly minted self-card the moment the name is confirmed, a peer's card the moment its pairing code is confirmed. Editing a field alone never persists. The suffix and iroh key are minted independently and survive an application-identity reset
- **trust is imported, never inferred.** A card arriving over card setup is verified as well-formed and correctly signed and nothing more; the PIN is ~35 bits and its rendezvous record is offline-attackable, so possession of the PIN must not be enough to become trusted. `SessionController.incomingCard` parks it for the pairing-code comparison and only `importIncomingCard()` writes it to the trusted list
- self-cards expire after 30 days and are re-minted at launch once inside the 7-day renewal window (`needs_renewal` from `DuocbNative.identityCardInfo`). A lapsed peer card cannot pair and renders in warning colour rather than vanishing — parsing is deliberately clock-free in the core
- the pure-Kotlin parts (`ClipItem` CRC/size display, `DuocbConfig` JSON, `SignalChannel`) have JVM unit tests: `./gradlew :app:testDebugUnitTest`. Run them and `:app:assembleDebug` after Kotlin changes. Gradle needs JDK 17 (`JAVA_HOME`)
- E2E: every CTA carries a Compose `testTag`, exposed as a `resource-id` to `uiautomator dump` (`testTagsAsResourceId`), so a harness taps by tag rather than coordinates. Debug builds also take an autostart from launch-intent extras (`app/src/debug/.../DebugAutostart.kt`: `adb shell am start -n com.andrewtheguy.duocb/.MainActivity --es duocb.autostart.role connect …`), the Android form of the iOS `DUOCB_AUTOSTART_*` env hook; the release source set replaces it with a no-op. Test on the local Android emulator (`emulator-5554`, relay-only) for UI, and on the LAN-bridged Android VM (`10.22.35.66:5555`) for direct paths; always pass `-s <serial>` / `ANDROID_SERIAL`
